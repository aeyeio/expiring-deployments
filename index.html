What it does well

Preview branches and ephemeral environments are great until they become permanent. Expiring Deployments provides a standard, auditable cleanup loop that reduces clutter and spend without risky “delete everything” automation.

Safe by default

Dry-run starts on. Protected namespaces are never touched. A circuit breaker caps how much can be deleted per run.

Metadata-driven

Opt in with annotations. Use expires-at or ttl-hours (with created-at fallback).

Preview-first

Selectors keep cleanup scoped to preview branches, QA sandboxes, and intended namespaces—nothing else.

Example usage

Pick the workflow that matches how your team ships preview environments.

Scenario A: Namespace per PR

CI creates pr-1234, applies a TTL, and the CronJob deletes it after expiry.

Annotate a namespace 
kubectl annotate ns pr-1234 \
  expiring-deployments.io/enabled="true" \
  expiring-deployments.io/ttl-hours="24" \
  expiring-deployments.io/owner="eng" \
  --overwrite

Scenario B: Shared namespace + expiring release

Add a lease marker ConfigMap to your chart. When it expires, the CronJob uninstalls the Helm release.

Lease marker ConfigMap 
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ printf "%s-ttl-lease" .Release.Name | trunc 63 | trimSuffix "-" }}
  labels:
    expiring-deployments.io/type: helm-release
    app.kubernetes.io/instance: {{ .Release.Name | quote }}
    app.kubernetes.io/managed-by: "Helm"
  annotations:
    expiring-deployments.io/enabled: "true"
    expiring-deployments.io/ttl-hours: {{ .Values.cleanup.ttlHours | default 24 | quote }}
    expiring-deployments.io/owner: {{ .Values.cleanup.owner | default "unknown" | quote }}

Uninstall

Remove the CronJob and its RBAC when you no longer need automated TTL cleanup.

Helm uninstall 
helm uninstall expiring-deployments
